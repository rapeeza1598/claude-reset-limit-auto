# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Docker container that pings the Claude Code CLI on a schedule (default 06:00/11:00/16:00/21:00 Asia/Bangkok — 5h apart except the 21:00→06:00 overnight gap, which is 9h) so the Claude.ai/Claude Code **subscription**'s rolling 5-hour usage window resets at predictable times instead of drifting with whenever the user happens to start working. The ping is a no-op if the user was already active during that window — it can't detect or override real rate-limit state, it just guarantees *a* window starts at the scheduled hour.

`docs/knowledge-base.md` holds the decision log, lessons learned, safe test recipes (never test with a real ping), and open items. Read it before changing the Dockerfile or the exec/cron path, and update it when you make a decision worth remembering.

## Commands

- `go build -o /tmp/reset .` — compile the Go binary locally
- `go test ./...` — run the test suite (`main_test.go`); `go test -run TestShouldPing/same_slot -v` for a single case
- `go vet ./...` — static check
- `docker compose build` — build the image (multi-stage; can be slow, since the `installer` stage downloads the Claude CLI native binary plus curl's TLS dependency chain)
- `docker compose up -d` — start the real service (needs a populated `.env`, see below)
- `docker compose up -d` — also applies a changed `.env` (`RESET_HOURS`, `PING_MODEL`) without rebuilding. `docker compose restart` does **not**: it reuses the container with its old environment
- `docker compose exec claude-reset <cmd>` — run a command inside the already-running service container. The final image is distroless (no shell, no coreutils), so `<cmd>` must be one of the binaries actually present: `/app/reset`, `/usr/local/bin/supercronic`, or the Claude CLI under `/home/appuser/.local/bin`
- `docker compose run --rm claude-reset <cmd>` — one-off container for debugging (`/app/reset -init` honors extra args by exec'ing them instead of starting the real service — see Architecture)
- `docker compose logs -f` — tail supercronic's + the reset binary's combined JSON logs

No CI: the GitHub Actions workflows were removed on 2026-11-18 (see `docs/knowledge-base.md`). Run `go vet ./...`, `go test ./...`, and `docker build .` locally before pushing. `SUPERCRONIC_VERSION` in the Dockerfile is a manual pin, since Dependabot's Docker ecosystem only tracks `FROM` lines, not `ARG`s.

## Required setup before running

`.env` (gitignored, copy from `.env.example`) needs `CLAUDE_CODE_OAUTH_TOKEN`, generated by running `claude setup-token` on a machine already logged into a Claude Pro/Max account. **Never set `ANTHROPIC_API_KEY` anywhere in this project** — Claude Code CLI's auth precedence picks it over `CLAUDE_CODE_OAUTH_TOKEN` when both are present, which silently bills a separate Console/API account instead of the subscription this tool exists to reset.

## Architecture

**`main.go`** (stdlib only, no third-party deps) hardcodes `/data/last_slot`, `/data/reset.log`, `/app/reset`, `/app/crontab`, and `/usr/local/bin/supercronic`, so the compiled binary can't be run standalone outside the container (`go build -o /tmp/reset . && /tmp/reset` fails opening the log file unless `/data` exists and is writable) — `go test ./...` is the way to exercise the logic locally. It dispatches on `os.Args[1]` into four modes:
- No args (a manual run): computes an hour-granularity slot key (`YYYY-MM-DD_HH`) and compares it against `/data/last_slot` — if that slot was already pinged, logs a "skip" entry and exits. The comparison itself is factored into `shouldPing()` so it's unit-testable without touching the filesystem or spawning a process. Otherwise shells out to `claude -p "hi" --model $PING_MODEL --tools "" --no-session-persistence` (`PING_MODEL` defaults to `haiku`) with a 5-minute timeout (supercronic never overlaps runs of a job, so a hung ping would block every later slot). The command inherits the container's environment, including the OAuth token, and the state file is written only on success — a failed ping (bad/expired token, network error) is left for retry at the next scheduled slot rather than marked done.
- `-scheduled` — the cron path. Same as no args, but first checks `onTime()`: if the fire is more than `lateGrace` (10 min) past an hour in `RESET_HOURS`, it logs a skip and doesn't ping. A fire up to `earlyGrace` (1 min) *before* the hour counts toward that hour (`slotStart()`), because on the Windows host supercronic routinely fires 1-3s early (10:59:57 for the 11:00 job); the slot key uses the same rounding. A sleeping host (Docker's VM paused on Mac or Windows) makes supercronic run the overdue job on wake, and a late ping would start the 5-hour window at the wrong time. Manual runs skip this check on purpose.
- `-init` — the container `ENTRYPOINT`. Regenerates `/app/crontab` from the `RESET_HOURS` env var (comma-separated hours, 0-23, validated by `parseHours()`; a bad value makes the container exit with an error) on every container start (so schedule changes only need `docker compose restart`, never a rebuild) via the pure, unit-tested `buildCrontab()`, logs `crontab written` with the hours, then execs `supercronic -json -passthrough-logs` on it — unless extra args were passed (`docker compose run claude-reset <cmd>`), in which case it execs those instead, so ad-hoc debugging doesn't accidentally spin up a second long-running instance of the real service.
- `-c <command>` — stands in for `sh -c <command>`; see the `supercronic`/`SHELL=` note below for why this exists. Splits `<command>` on whitespace and execs it, which in practice always re-enters the ping path as `/app/reset -scheduled`.

Logs every run as JSON (`log/slog`) to both stdout and `/data/reset.log`, so history survives container recreation via the `/data` volume.

**`Dockerfile`** is 3 stages:
1. `builder` (`golang:1-alpine`) compiles the static (`CGO_ENABLED=0`, stripped via `-ldflags="-s -w"`) Go binary.
2. `installer` (`debian:trixie-slim`) fetches the Claude CLI native binary and `supercronic`, and prepares everything the shell-less final stage can't create for itself: an `appuser`/home layout for the Claude CLI's installer (it symlinks `~/.local/bin/claude` to an absolute path under `~/.local/share/claude/versions/<v>`, so copying the tree between differently-named home directories would leave a dangling symlink), plus `/appdata/app` and `/appdata/data` (pre-chowned to `appuser`, later copied to `/app`/`/data` in the final stage since it has no `mkdir`/`chown`). This stage needs `curl` and its large TLS dependency chain (openssl/libcurl4/krb5/ldap/...), none of which ships in the final image — only the resulting binaries and metadata get copied out.
3. Final stage: [distroless](https://github.com/GoogleContainerTools/distroless) `gcr.io/distroless/base-debian13` — glibc, libssl, ca-certificates, tzdata, and DNS resolution (`netbase`/`nsswitch.conf`) bundled, but **no shell, package manager, or coreutils**. Non-root `appuser` (via `/etc/passwd`/`/etc/group` copied in from the installer stage), with just the compiled binary, Claude CLI, and supercronic copied in. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` turns off the CLI's autoupdater and telemetry. `docker-compose.yml` adds `cap_drop: [ALL]` and `no-new-privileges`, and `.dockerignore` keeps `.env`, `data/` and `.git` out of the build context.

**No system cron.** The container runs [`supercronic`](https://github.com/aptible/supercronic) instead — it needs no root (system cron requires root to write `/etc/cron.d` and manage per-job privilege-dropping), and spawned jobs inherit its process environment directly, so no `/etc/environment`-passthrough hack is needed either. supercronic invokes every scheduled command as `exec.Command(shell, "-c", command)`, where `shell` normally defaults to `/bin/sh` — but it reads a `SHELL=` line from the crontab file itself (Vixie-cron style) if present, and `main.go`'s `-init` mode writes `SHELL=/app/reset` into the generated crontab. That makes supercronic invoke `/app/reset -c /app/reset` instead of `/bin/sh -c /app/reset`, which is the only reason this service can run in a shell-less distroless image at all.

## Non-goals

No token renewal/rotation, no log rotation, no failure alerting, no real rate-limit introspection (the state file only tracks "did we already ping this hour," not actual usage) — all deliberate per the README's scope-cuts section. Don't propose adding these unless asked.
